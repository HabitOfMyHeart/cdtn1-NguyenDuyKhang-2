# L2 case-study extract

This is a bounded extract from `CDTN1_Mekong Mobile_Dataset Smart CRM/dataset`, not a copy of the full source. It contains 50 tickets, their complete 192 status-log rows, 34 customers, 50 devices, and tickets covering all six service centers and six issue categories. The source is a supplied case-study dataset; this project does not independently establish whether the source itself describes real people or events. Treat the included customer data as sensitive.

## Reproduction and provenance

Run `python scripts/extract_l2_dataset.py <source-directory>` to rebuild `l2_seed_sample.json`, or add `--output <path>` to write elsewhere. The extractor reads `tickets_history.csv`, `ticket_status_log.csv`, `customers_raw.csv`, and `products.csv`. The six catalog files were mapped from the source `service_centers.csv` and `issue_categories.csv`; `products.json` is the previously extracted catalog and is not used by the seed. The legacy mapping file contains only ticket codes and internal IDs, not names, phones, or addresses. It anchors the original 30 ticket/customer/device IDs and 99 traceable log IDs. All other IDs use `SRC-` plus the source ticket, customer, or log ID. Source ticket codes identify source rows. Selection starts with those 30 rows, then prefers other tickets belonging to the same source customers, followed by other customers, in ascending history length and source ticket ID, with unique normalized phones and serials. All original log rows for each selected ticket are included.

Ticket status, priority, warranty flag, dates, center, category, description, and code come from the source ticket; log transition, time, actor and note come from the corresponding source log. Dates in ticket/log CSVs are interpreted as UTC+07:00 local time. Log actors are prefixed `NV_` (or `SYSTEM` if empty). Customer names, phones, email, address and creation date come from the source customer; phones are normalized to ten digits. Product and warranty-month fields come from the source product; device serial comes from the ticket. A device is associated with its ticket's source customer. Catalog field names are adapted to the application schema; center `is_active` is an application default.

Application defaults, not source claims: customer `segment=THUONG`, `is_deleted=false`, empty accessories/exterior note/priority reason, and device `purchase_date=null` (source tickets lack purchase dates). If a customer creation date is absent, ticket receipt time is used. The source ticket's warranty flag is retained independently of the unknown purchase date. Unlike the old sample, no ticket is forced to `MOI`, no log is fabricated or truncated, and no purchase date is invented. Consequently legacy IDs can now have different content.

Run `node --test tests/dataset-scope.test.js` for offline integrity/schema checks. Set `DATASET_SOURCE` to the original directory before running the same command to additionally re-extract to a temporary file and compare the complete result. The source is not required for offline checks.

## Safe seeding and conflicts

`node seeds/seed_l2_data.js --plan-safe` (or `--check`) reads the configured database with the native MongoDB driver, without creating collections or indexes. It reports counts, proposed business IDs, and conflicts by field name, not customer values. Existing rows match only when every supplied sample field matches after schema casting; additional database fields are not compared. In particular a different device `purchase_date` blocks reuse, even if serial and customer match: no identity is inferred solely from a key. Divergent or unresolved parent references block their tickets and all associated sample logs. An already present ticket qualifies for logs only when it and all of its parents match; new tickets must also pass the modeled one-open-ticket-per-device constraint. Only parents needed by eligible tickets are proposed. The source-compatible count excludes logs attached to ineligible parents, even if those logs already exist. Collection totals include all existing data and do not imply it is source-compatible.

The plan is a projection; the confirmed add-safe mode imports only its proposed additions. Default `npm run db:seed` inserts only into an empty database or one containing only matching sample records; it aborts before writes if other rows or conflicts are present. For a mixed existing database, `--add-safe` requires the separate `--confirm-add-safe` flag and inserts only the source records the planner found nonconflicting; it never updates or deletes existing rows. On 2026-10-27 the main database was backed up to `C:\Users\ACER\AppData\Local\Temp\opencode\mekong_warranty-backup-20261027` before an approved add-safe run inserted 4 customers, 20 devices, 20 tickets, and 85 logs. Post-write verification found no changed or missing old documents, no orphan new logs, and no device with two open tickets; totals became 35 customers, 50 devices, 50 tickets, and 188 logs. A separate temporary clean database on port 27018 was migrated and seeded twice: the first run loaded 34 customers, 50 devices, 50 tickets, and 192 logs; the second run kept the same counts with zero duplicate keys. The temporary database was dropped afterwards; see `docs/evidence/final/clean-seed-check.txt`. The 51 old records that differ from the source remain unchanged, so totals meet the scope range but the database is not a source-identical copy. The planner checks schema validation and modeled keys but does not verify every database index or ensure an atomic concurrent-write strategy. Stop other writers, run migration first on an approved clean target, and inspect failures: insertion across collections is not transactional and may be partial. Preserve existing documents; do not overwrite or delete them to resolve conflicts. Existing IDs such as `CUS0022`/`DEV0022` alone do not prove identity.
